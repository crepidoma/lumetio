# 不具合を直す

## 1. 決まりを確かめる

- 期待する動きを、設計書（`documents/design.md`）で確かめる。
- 設計書に書かれていなければ、決めずに相談する。
  決まったら、設計書に書き足してから直す。
- 優先順位（AGENTS.md の「このアプリの優先順位」）に関わるもの（日次ファイルを壊す、他の PC の変更を上書きする、操作していない日のファイルを作る）は、ほかより先に扱い、報告でもそう伝える。

## 2. 再現するテストを書く

| 不具合の場所 | テスト |
| --- | --- |
| Go の決まり（`internal/`） | 同じパッケージの `*_test.go` |
| 画面の部品 | `frontend/src/*.browser.test.tsx`。書き方は [frontend-test](../frontend-test/SKILL.md) |
| 画面の関数（並びの計算など） | `frontend/src/*.test.ts`。Node で動く |

- テストの名前は、守る決まりを日本語で書く（例: `日を移ったら、前の日の打ちかけの内容を移った日に書かない`）。
- 値は架空にする。実在の名前や課題番号を使わない。
- 画面の不具合でも、決まりが Go にあれば Go のテストにする。
  画面のテストより速く、MCP の側も同じ決まりで守れる。

## 3. 直す前のコードで落ちることを確かめる

テストを書いた後、直す前のコードでテストを動かし、**落ちること**を見る。
通ってしまうテストは、その不具合を再現していない。

- 直しを先に書いてしまったときは、直したファイルをコミット済みの版に戻して動かし、元に戻す。
  直しの一部だけを戻すと、直す前と違う状態になり、関係のないテストまで落ちることがある。

  ```sh
  cp <file> <scratchpad>/<file>.bak
  git show HEAD:<path> > <path>
  # テストを動かす
  cp <scratchpad>/<file>.bak <path>
  git diff --stat <path>   # 戻せたかを確かめる
  ```

- 画面のテストは、Chromium と WebKit の両方で落ちるかを見る。
  片方だけで落ちるなら、どちらの不具合かを報告に書く。
- 直す前でもテストが通るとき（タイミングで表に出ないなど）は、そのテストを振る舞いを守るものとして残してよい。
  報告では、再現していないことをそのまま書く。

## 4. 直す

- 症状を消すのではなく、原因を直す。
  同じ原因でほかに起きている場所がないか探し、あれば一緒に直してテストを足す。
- コメントは、守っている決まりか「なぜ」を書く。
  経緯（「〜のバグを直した」）は書かない。

## 5. 完了の定義を通して報告する

AGENTS.md の完了の定義をすべて通す。
報告には次を書く。

- 何が起きていたか（ユーザーから見た症状）と、原因
- 足したテストと、直す前のコードで落ちたか
- 確かめられなかったこと（画面の見た目、macOS など）

コミットは、ユーザーが差分を確かめてからにする。
